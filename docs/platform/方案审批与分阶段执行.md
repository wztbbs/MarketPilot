# 方案审批与分阶段执行

权限仍以 Tool 为粒度。PreparedToolCall 是本次确定的工具调用实例，不是 CapabilityDefinition 或独立的业务操作权限目录。PreparedPlan 将这些调用组合成一份可审批方案；批准方案不扩大 Agent 的工具绑定和用户的数据权限。

## 阶段 1、2 的接入契约

| 对象 | 职责 |
| --- | --- |
| PreparedToolCall | 调用 ID、工具名、参数或参数引用、显式依赖 |
| PreparedPlan | 方案摘要、调用清单、有效期、STOP_ON_FAILURE 规则 |
| PlanApprovalStatus | PENDING、APPROVED、REJECTED、EXPIRED、SUPERSEDED，表示审批决定及有效性 |
| PlanExecutionStatus | NOT_STARTED、RUNNING、WAITING、SUCCEEDED、FAILED、PARTIAL，表示执行进度 |
| RunWaitTarget | 明确区分 TOOL_CALL 与 PLAN_APPROVAL，均须归属于本运行、本用户 |
| ToolApprovalMode | 服务端适配器选择 PER_CALL 或 PREPARED_PLAN，默认保留逐调用确认 |

PreparedPlan 不是模型随时可以修改的规划草稿，也不等同于 CEX 的 CompiledPlan。方案提交后按稳定 slot 冻结；重复进入同一位置复用原方案，同一 slot 提交不同内容会被拒绝。只有尚未登记工具调用的方案可以 supersede，修改后用新 slot 创建新方案，必须重新确认；已开始的方案保留执行历史，通过后续阶段处理。

参数引用沿用底座 DAG 语法，例如 `{{create.data.id}}`。必须显式声明依赖，不允许循环依赖或引用不存在的调用；准备时按输入 Schema 检查参数，并核对上游输出字段。执行时只用真实成功结果解析引用，再做完整参数、权限及资源版本检查，不允许让模型临时决定新的写操作。

```java
var proposal = new PreparedPlan("创建工单并指派人员", List.of(
    new PreparedToolCall("create", "ticket.create", createArguments, List.of()),
    new PreparedToolCall("assign", "ticket.assign", assignArguments, List.of("create"))
), 3600);
// assignArguments 中的 ticketId 可以是 {{create.data.id}}。
```

## 共用链路

```text
服务端适配器选择 PREPARED_PLAN
→ 准备已授权的只读信息
→ PreparedPlanService.prepare(slot, proposal)
→ 冻结身份、工具契约、参数／引用、摘要、资源版本、有效期和指纹
→ RunStep.waitingForApproval(planId)
→ 用户确认整份方案
→ RunCoordinator 恢复原 Agent／适配器
→ PreparedPlanExecutor.execute(planId)
→ ToolGateway.invokePrepared(planId, callId)
→ 真实提交／异步等待／恢复，最终幂等提交业务结果
```

是否需要人工确认仍来自工具定义：方案中任一工具要求 confirmationRequired，整份方案进入 PENDING。全部工具均不要求确认时，由 TOOL_POLICY 自动批准，记录与用户审批不同的决定来源。方案模式中的 OPERATION 不能走原始 invoke 绕过方案；准备阶段的 READ 仍可正常使用。

方案审批前检查工具绑定，以及已经确定参数的权限和目标版本。依赖尚未产生结果的调用，准备／确认阶段先检查绑定；参数解析后必须执行完整的数据权限及资源版本检查。对未知资源提前通过一次泛化的数据权限检查不构成执行授权。

实际执行仅接受 planId 和 callId。工具、参数、身份、调用位置均由服务端从获批方案恢复。后台提交、轮询和查单也核对方案归属、内容指纹、工具契约和实际参数，不能只信任工具调用记录里的 approved 标记。

## 等待、失败与恢复

方案审批状态与执行状态分别保存。等待审批不会生成待执行的操作 CALL，也不会扣工具预算。审批 HTTP 请求只记录决定并唤醒运行，不执行工具。

首版 PreparedPlanExecutor 按拓扑顺序串行执行。异步工具受理后保存真实 jobId、暂停运行；完成后恢复同一个调用位置，复用原结果，不重复扣工具预算。后续参数由已批准的引用规则确定，不重新调用模型解释授权范围。

任一调用失败即停止后续调用。全部成功为 SUCCEEDED；没有成功调用时失败为 FAILED；已经存在成功调用而后续失败为 PARTIAL。已完成的外部操作不会自动回滚，未开始的调用与真实结果分别展示。拒绝或过期不会产生工具副作用。

有效期取方案、工具及所属 Run 的约束。过期后不能开始新操作；等待过期结束的是系统等待，不证明外部任务没有发生或已经被取消。修改方案、追加动作或改变引用规则需要新方案及新审批。

## 持久化与并发

新增 `platform_prepared_plan`，已同步加入 schema.sql 和 migrations/023_prepared_plan.sql。审批状态、归属和调度时间为列；不可变内容、指纹、执行状态及决定保存在 JSON 文本中，沿用 DurableStore 的 revision CAS。

创建方案、确认决定、废弃方案及首次调用登记使用短事务，按 RUN → PLAN → CALL 加锁。首次调用登记与方案废弃串行化；已登记调用后不再允许用新内容替换方案。业务权限服务、资源版本查询和外部工具执行不放进数据库事务。

RunReconciler 同时扫描 Run、CALL 和方案到期记录。确认后的唤醒与到期扫描共同补偿漏消息。租约失效的旧执行者不能创建或推进新方案。

## API 与页面

| 接口 | 用途 |
| --- | --- |
| GET /api/agent-runs/{runId} | 返回运行、方案、调用及逐步结果；plans 包含审批状态与执行状态 |
| POST /api/agent-runs/{runId}/plans/{planId}/decision | JSON 为 fingerprint、approve；要求 X-Agent-Action: 1 |

身份沿用服务端访客 Cookie。其他访客或其他 Run 不能确认该方案；重复同意／拒绝幂等，反向决定冲突，错误指纹拒绝。页面展示整份方案、参数引用、依赖、资源版本、有效期与逐步结果；已绑定方案的 CALL 不再重复展示逐笔确认按钮。

原逐调用确认接口仍保留，两种模式不会互相扩大权限。

## 阶段 3：声明式 Plan 接入

声明式 Agent 在 YAML 中选择 `tool_approval: prepared_plan`，PlanEngine 使用 plan_base_prepare＋业务说明生成 DAG，校验后冻结为 PreparedPlan，在任何节点执行之前等待整份方案审批。参数引用自动推导依赖，也支持 depends_on 显式表示没有参数引用的先后关系。

批准后使用共用 PreparedPlanExecutor，按原方案依赖顺序执行；恢复时复用已完成结果，不再次规划或提交。模型最终回答只能引用真实成功节点。方案部分失败时保留真实成功结果，轮次标记 FAILED／PARTIAL，不把部分操作成功包装成整份方案成功。

未声明 prepared_plan 的 Agent 继续使用原 Plan／DAG 路径。业务 PlanHooks 与 Query 的 planSelfDriven 算法保持原样，不自动接管其业务审批生命周期。

## 阶段 4：ReAct 分阶段接入

同一配置项用于 ReAct。ReactEngine 将方案模式委托给 PreparedReactExecution，使用 react_base_prepare＋业务说明＋工具契约：

- call：只允许 READ；直接 call 操作工具会作为模型协议错误反馈修复，不执行操作。
- propose：提出本阶段的调用清单、参数、依赖与摘要，形成不可变审批方案。
- finish／clarify：根据真实观察结束或澄清，不伪造未执行工具的成功结果。

准备时的只读观察可用 `$ref` 对象取值并冻结为确定参数；方案内部尚未执行的调用使用 `{{callId.data.field}}` 表达经审批的依赖。两类引用分别解析，不能让模型在批准后重新选择参数或操作。

每阶段的已校验决策、确定方案、真实观察和累计计数先写入固定检查点，再登记审批方案。审批后恢复直接使用检查点，不重新调用准备模型、不重新查询，也不重新从可能过期的只读观察推导已冻结参数。阶段模型日志使用 agent_prepare_1、agent_prepare_2 等稳定位置，跳过旧阶段不会错误复用其他阶段的响应。

操作完成后，下一阶段模型接收真实结果。如果还需要新的操作，必须 propose 新方案，并按工具确认规则重新审批；失败则停止后续操作。阶段决策总数仍受 max_steps 和跨等待累计预算限制。高精度数值在准备检查点、冻结参数、已完成结果和后续引用中使用 BigDecimal 保留。

## 声明式配置示例

```yaml
id: ticket_assistant
route: tickets
description: 根据用户请求创建并指派工单
enabled: true
engine: react  # 也可为 plan
prompt: ticket_assistant
tool_approval: prepared_plan
allowed_tools: [ticket.lookup, ticket.create, ticket.assign]
execution:
  max_steps: 8
  max_model_calls: 12
  max_tool_calls: 12
  timeout_ms: 180000
```

tool_approval 只支持 per_call／prepared_plan，省略时为 per_call，非法配置启动失败。配置变更会改变运行协议指纹；不能把等待中的方案运行切换成逐调用模式继续执行。方案有效期默认上限 24 小时，再取工具与所属 Run 的更短限制。

配置只是启用执行协议。业务仍须实现工具、正确的绑定和数据权限、资源版本校验、幂等或查单协议，以及领域提示词；不会由这项配置自动生成业务能力。
